# Emoji Match: native picker parity and owned expressive-image history

Audit date: 2026-11-15. Scope: read-only source, SDK and existing runtime evidence review; current primary Apple documentation. This audit creates only this document. No desktop UI, new runtime generation, source edits, agents, commits or account changes were performed by this research agent. The lead supplied the receiver runtime results during the audit; their source and output artifacts were inspected here.

## Decision

**An app-owned list of captured Genmoji is feasible without private sticker-database access.** Both selecting an existing system Genmoji and creating a new one delivered an `NSAdaptiveImageGlyph` into an app-owned native `NSTextView` in the lead's tests. The system picker remains responsible for its library and creation UI. Emoji Match can retain the delivered bytes, display them in its own list, and implement reuse. The production app does not yet implement that receiver, typed history or rich paste.

**Enumerating the user's complete system sticker/Genmoji library remains blocked by the investigated private database interface.** A user-mediated picker selection is an authorized delivery of one item, not authorization or an API for bulk enumeration. No public macOS library enumeration API was identified in the reviewed Apple documentation and SDK. This is a bounded finding, not proof that no future or separately approved Apple interface could exist.

**Comprehensive native parity has substantial ordinary implementation gaps as well as platform boundaries.** Unicode variants, favorites, richer search, symbols, accessible navigation and app-owned history can be built. Exact system collection synchronization, all recipient integrations and the native compact creator embedded inside our own custom list cannot currently be promised. Keep an explicit system-picker escape route while closing the buildable gaps. That preserves access to system-only functionality without describing the custom browser as already equivalent.

## The newly proven public input-client route

### Bounded proof

The lead ran `/tmp/emoji-match-genmoji-ui/receiver.swift`. This agent inspected that file: lines 5–7 create a rich-text, graphics-importing `NSTextView`, make it first responder in a key app window, activate the app, then call `NSApp.orderFrontCharacterPalette(nil)`. Lines 9–13 enumerate `.adaptiveImageGlyph` in `textDidChange` and save `imageContent`. No private sticker database call appears in that receiver.

Tests ran on the lead's macOS 27.2.1 Apple Silicon setup. This research agent did not perform those clicks. Owned durable history, own-grid rendering, final paste back to the original app, cancel/focus recovery and ordinary sticker/Memoji payload types were **not** implemented or proven by these receiver tests.

The public contract is real: [NSTextInputClient](https://developer.apple.com/documentation/appkit/nstextinputclient.md) advertises adaptive glyph support and insertion; [orderFrontCharacterPalette](https://developer.apple.com/documentation/appkit/nsapplication/orderfrontcharacterpalette(_:).md) opens the palette. Installed SDK `AppKit.framework/Headers/NSTextInputClient.h:119–121`, `NSApplication.h:329`, and `NSAdaptiveImageGlyph.h:21–43` confirm support, insertion, image bytes, durable content identifier, description, secure coding and attributed-string construction. Apple explains the expressive-image rich-text model in [Bring expression to your app with Genmoji](https://developer.apple.com/videos/play/wwdc2024/10220/). These APIs receive a user's selection; they do not expose the system library as a collection.

### Production architecture to implement

One app-local import/creation session should own this lifecycle:

1. Capture original PID/app, focused AX input, supported selection/caret evidence and a unique session token before changing key focus. Avoid stale target reuse.
2. Present an understandable app-owned receiving surface. Give an editable native `NSTextView` `isRichText = true`, `importsGraphics = true`, a real key window and first-responder ownership. Check `supportsAdaptiveImageGlyph`; do not assume an invisible/nonactivating search panel behaves like the proven receiver.
3. Invoke `NSApp.orderFrontCharacterPalette(nil)` while that receiver owns input. User selects a system item or creates one. The current handoff-to-original implementation must be a separate mode: it cannot also collect this callback.
4. Inspect inserted rich content through native insertion/text-storage observation. Extract `.adaptiveImageGlyph`, and separately classify ordinary attachments/images. Deduplicate per session/change so enumerating the whole text storage repeatedly does not inflate history. Handle Unicode selection, multiple insertions and cancellation explicitly.
5. Persist the obtained asset and metadata atomically. Capture/import is not usage: show the new item in an imported/created section even before successful use; increment usage only at the chosen, accurately named insertion boundary.
6. For “insert into original app,” close receiver/picker, verify the session still owns that operation, restore the captured live target, and rich paste only after focus is established. A user switching applications must not cause a paste into the new frontmost app. If target identity cannot be restored, keep the item and offer an explicit copy/retry.
7. On cancel, timeout, target destruction or supersession, invalidate token, stop observations, release key receiver and restore appropriate focus without inserting. Late callbacks cannot trigger a paste after cancellation. A captured item and an abandoned insertion are separate states.

Keep this feature under the app's targets, not root SwiftPM: receiver, focus/session owner and rich paste are app-specific. Shared catalog types remain reusable Unicode data. Introduce an app-local selection payload boundary rather than passing private XPC objects through search/UI models.

## Owned history data and display

Recommended model (**I**, not implemented):

- `unicode`: canonical scalar-sequence ID plus exact insertion string; variant identity must not collapse to the base ID.
- `adaptiveGlyph`: content identifier, original `imageContent` asset reference, byte hash, description, optional user label/tags, import/creation provenance and schema version.
- `imageSticker`: original supported image/attachment data, type and animation information where available; app-owned ID/hash and user description. Do not relabel a PNG as an adaptive glyph merely because it looks like a Genmoji.
- Common metadata: created/imported/last-used dates, count, favorite/pin status, content kind and local deletion state. Preserve original glyph bytes separately from thumbnails; bound both item count and total disk bytes.

Store assets in app-owned Application Support with transactional metadata; migrate existing v1 Unicode history without erasing counts or timestamps. Do not put large base64 glyph data in the current UserDefaults records. Key adaptive assets by stable content identity with hash verification; do not assume a private sticker UUID can substitute for stored bytes. Local deletion removes our asset when unreferenced, not the system original. System deletion must not invalidate an intentionally imported local copy. Add schema/corruption recovery, deduplication and automatic cleanup of temporary files.

Render adaptive glyph cells using a small native attributed-text view or a faithful cached image preview, preserving bytes for insertion. Use `contentDescription` for accessibility/search, with editable labels when descriptions are poor; literal descriptions are not exhaustive semantic indexing. General images use their actual image renderer. Combine Unicode, captured glyphs and imported stickers in own recents/favorites/search while retaining kind indicators and type-specific actions. Plain `Text(selection.value)` cannot do this.

Rich paste should construct an attributed string carrying `.adaptiveImageGlyph` (public SDK provides the convenience constructor) and serialize a verified rich pasteboard representation such as RTFD. Preserve the original glyph payload; support appropriate image export separately. Publish multiple representations only after testing the receiver's type preference. A bare replacement character or textual description is not rich glyph delivery. Unsupported plain-text targets need an explicit copy-image/description choice; neither has the same semantics as inline Genmoji.

## What blocks system library enumeration

Prior runtime investigation establishes this chain: `CPKGenerationRemoteViewController` hosts Apple's compact service and generates; callback is `NSUUID`; `STKImageGlyph.fromStickerIdentifier` → `createStickerWithAllRepresentations` → adaptive-glyph conversion requires privileged sticker access. The ordinary helper was rejected by `com.apple.stickers.api`; daemon inspection identified `com.apple.private.stickers`. A disposable ad-hoc helper claiming it was killed by macOS. See [Genmoji investigation](emoji-match-genmoji.md), `/tmp/emoji-match-genmoji-ui/resolve.m`, `resolve-log.txt`, `stickers-log.txt`, `how-cpk-disassembly.txt`, and `how-addresses.swift`. These are OS-build-specific private implementation findings, not supported integration constants.

The obstacle is daemon authorization and unavailable public collection access, not missing Swift syntax, guessed callback ABI, or inability to render the compact UI. Accessibility permission, loading StickerKit, a known UUID, ordinary signing or adding a private entitlement string do not establish those rights. No public authorization prompt or requestable entitlement for whole-library macOS enumeration was found in this audit. Public Messages sticker browser APIs describe app-provided sticker content and UIKit/iMessage surfaces; they are not evidence of reading the user's complete system collection from a macOS utility.

The **authorized alternative found here is public user-mediated delivery**: system UI resolves a selected item into our input client. It supports local copies of known selections, including new creations, without claiming database rights. It cannot enumerate unselected items, mirror hidden categories, observe all system creations/deletions or synchronize Apple's recents ranking. Separately, user-driven copy/paste/drop can import available representations. An absolute requirement that every system item immediately appear in our own custom grid without user selection remains unmet.

## Staged implementation and acceptance gates

1. **Freeze capability contract and preserve proof.** Update spec in the eventual behavior change: distinguish direct-to-original native handoff, owned receiver capture, local library, imported images and system library. Preserve receiver helper, OS build, selected/created artifacts and hashes in verification documentation. This audit alone changes no product contract.
2. **Implement owned assets/history and rendering.** Add typed selection, versioned metadata/asset store, migration, bounded storage, local delete/favorites/search and rich cells. Validate exact glyph-byte roundtrip, stable ID/description, deduplication, corrupt asset recovery, migration and cleanup. Use existing real glyph fixtures, not screenshots or synthetic strings as fidelity evidence.
3. **Implement session-owned receiver and rich delivery.** Build the proven native client into an app-local import/create flow. Test selected existing and new glyphs, cancellation before/after creation, double callbacks, multiple picks, rapid reopening, target close, switch app/space, permission changes and late events. Then validate end-to-end own grid → TextEdit and Notes with copy-back identity/bytes. Add slow-reader and intervening-copy clipboard checks. Preserve prior clipboard only while it remains ours.
4. **Test expressive-image coverage explicitly.** System recents/favorites selection, new Genmoji, Memoji, static sticker, Live Sticker/animation and pack sticker each need their own actual payload/type result. Test ordinary native text fields, rich text, browser contenteditable and Electron individually. Report denominators, losses and fallbacks. Plain Safari contenteditable already lacked native Genmoji in the original-recipient flow; the receiver may capture anyway, but that does not make the final target accept it.
5. **Close Unicode picker gaps.** Tone/multi-tone and gender relationships, favorites, full search results, usable clear/history controls and full keyboard/VoiceOver flows. Expand symbols/inspector/settings as deliberate parity work; preserve native fallback throughout. Validate unsupported sequences and OS rendering rather than weakening inventory assertions to match the current grid.
6. **Add optional enhancements after compatibility gates.** Intent ranking, custom collections, editable labels, larger inspector and app-owned sync. Keep scope independent of Apple's private databases and state unsupported recipient boundaries in product behavior.

Follow-up implementation can proceed with the receiver architecture now; no further private-database investigation is required for owned Genmoji history. The remaining high-risk work is robust session/focus ownership, faithful rich transfer, storage and receiver compatibility. Full system library enumeration remains a separate unresolved platform capability, not a prerequisite for saving the glyphs our app actually receives.

## Audit method and remaining uncertainty

Apple Developer URLs were tried with `.md` first. Some endpoints returned unsupported Markdown content-type or cache errors; public installed SDK declarations supplied the exact API signatures where web retrieval failed. No new desktop/native compatibility test was run by this research agent. Native font inspector details, ordinary sticker payloads, full current category inventory, VoiceOver interaction, system sync behavior and cross-version behavior remain unverified as marked above. Source review and successful one-machine Genmoji capture do not establish universal recipient support.
